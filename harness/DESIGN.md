# 장학금 자동 수집·분류 하네스 — 설계안

**작성** UniSco 팀 · **상태** 구현 완료(2026-08-04, `harness/` 참고) · **버전** v1

---

## 1. 배경

UniSco는 대전 지역 대학생 대상 장학금 매칭 서비스로, 현재 10개 대학·366건의 장학금 데이터를 보유하고 있다. 데이터는 팀원 한 명이 각 대학·학과 홈페이지를 수동으로 방문해 공고문을 읽고, 구조화된 필드(자격조건·금액·마감일 등)로 직접 변환해 입력하는 방식으로 수집돼 왔다.

이 방식은 다음 이유로 확장하기 어렵다:

- 학교 하나를 온전히 커버하려면 대학 공통 장학금뿐 아니라 **모든 개별 학과의 장학 공지 게시판**까지 훑어야 하는데, 이 작업량이 학교 수에 비례해 선형으로 늘어난다.
- 수동 검토라 이미 수집한 장학금과 신규 항목을 구분하는 것, 마감이 지난 항목을 정리하는 것도 전부 사람이 기억에 의존한다.
- 공고문 상당수가 HTML이 아니라 PDF·이미지·한글(HWP) 첨부파일로 제공된다.

이 문서는 위 과정 중 **"공고문 원문 → 구조화된 데이터"** 구간을 LLM 기반으로 자동화하되, 이 종류의 자동화에서 흔히 발생하는 두 가지 실패 모드(누락, 할루시네이션)를 설계 단계에서부터 억제하는 방안을 제시한다.

## 2. 목표와 비목표

**목표**

- 신규 대학 1곳을 온보딩하는 데 드는 사람의 노동을 "일일이 찾아 읽고 입력"에서 "초안을 검토하고 승인"으로 낮춘다.
- 자동화된 단계에서 발생하는 오류(빠뜨림, 지어낸 값)를 최종 반영 전에 기계적으로 잡아낸다.
- 기존에 이미 검증된 워크플로(GitHub PR 리뷰, `run_sql.py`를 통한 수동 반영)를 재사용해 새로운 신뢰 경계를 만들지 않는다.

**비목표 (이번 설계에서 다루지 않음)**

- 완전 자율 수집·반영 (사람 승인 없이 운영 DB에 바로 쓰는 것)
- 대학 공식 사이트가 아닌 출처(커뮤니티, SNS 등)에서의 수집
- 이미 구조화 완료된 기존 366건의 재검증 (별도 논의 대상)

## 3. 두 가지 핵심 실패 모드와 대응

자동화된 웹 조사·추출 파이프라인에서 실제로 반복 관찰된 문제는 두 가지다. 원인이 다르므로 대응도 각각 다르게 설계한다.

### 3.1 누락 — "다 봤다"는 판단을 에이전트에게 맡기지 않는다

에이전트가 "이 정도면 다 확인했다"고 스스로 판단하게 하면, 장시간 작업일수록 조기 종료·페이지네이션 누락이 발생하기 쉽다. 이를 **검증 가능한 문제**로 바꾼다:

1. 학과 페이지 진입 시, 장학 공지 게시판의 **총 게시물 수/총 페이지 수**를 먼저 기계적으로 파싱한다.
2. 1페이지부터 마지막 페이지까지는 에이전트 판단이 아니라 **코드로 반복 순회**하며 링크만 수집한다.
3. LLM은 "수집된 링크 목록의 각 항목을 읽고 구조화"하는 마지막 단계에만 관여한다.
4. 처리 완료 후 `수집된 항목 수 == 게시판에 표시된 총 항목 수`를 기계적으로 대조해, 불일치 시 자동으로 재시도하거나 리뷰에 플래그를 남긴다.
5. JS 렌더링에 의존하는 사이트(예: 특정 대학 단과대 페이지에서 이미 확인된 사례)는 단순 HTTP 요청 대신 헤드리스 브라우저(Playwright)로 렌더링 완료 후 텍스트를 가져온다.

### 3.2 할루시네이션 — 구조화된 값마다 "원문 인용"을 강제하고 기계적으로 대조한다

핵심 아이디어: **필드값을 추출할 때, 그 근거가 된 원문 문장을 요약 없이 그대로 함께 출력하게 하고, 그 인용문이 실제로 원문에 존재하는지 코드로 대조한다.** 인용문이 원문에 없으면 그 필드는 지어낸 것으로 간주해 자동으로 "확인 필요"로 전환한다.

이 방식이 유효한 이유: 모델이 값을 지어낼 때는 그 값을 뒷받침하는 원문 그대로의 문장을 함께 만들어내지 못하거나, 만들어도 원문에 없는 문장이라 문자열 대조에서 바로 걸러진다. 반대로 실제로 원문을 근거로 뽑은 값은 인용문이 정확히 일치한다. 이건 프롬프트로 "정확하게 해줘"라고 부탁하는 것과 달리, **자동으로 검증 가능한 필터**라는 점이 다르다.

보조 장치:

- **한 번의 추출 호출 = 공고문 하나만 노출.** 여러 공고문을 누적해서 기억하게 하면 서로 다른 장학금의 조건이 섞이는 사고가 발생하기 쉽다. 상태 없이 "텍스트 1건 → 구조화 결과 1건"으로 독립 처리한다.
- **금액·학점·마감일 등 숫자 핵심 필드는 독립적으로 2회 추출해 서로 대조.** 불일치 시 자동으로 리뷰 대상.
- **"원문에 없으면 추정하지 말고 비워둘 것"을 명시.** 인용 강제와 결합하면, 빈 값도 "왜 비웠는지"(인용 실패)가 남아 검토가 빨라진다.
- **출력 스키마를 구조화(tool-use/함수 호출)로 강제**해, 존재하지 않는 분류값(enum)을 만들어내는 것 자체를 원천 차단한다. UniSco는 이미 자격조건 enum(장애유형·특수상황·어학시험 종류 등)과 각 필드의 의미를 상세히 문서화해 두었으므로, 이 문서 자체를 프롬프트 재료로 재사용한다.

## 4. 전체 파이프라인

```
[1] 목록 수집 (기계적, 결정적)
    대학 공통 페이지 + 전 학과 페이지 순회
    → 게시판별 총 개수 파싱 → 페이지 전체 순회 → 공고 링크 목록

[2] 원문 확보
    HTML은 그대로, PDF/HWP/이미지는 텍스트 추출 (기존 extract_text.py 재사용)

[3] 중복·스테일 스킵 (기계적, LLM 아님)
    이름+기관 문자열 유사도로 기존 DB와 대조 → 이미 있는 건 스킵

[4] 구조화 추출 + 근거 인용 (LLM, 문서 1건 = 호출 1건)
    스키마 강제 출력 + 필드별 원문 인용 동반

[5] 자동 검증
    인용문이 원문에 실제 존재하는지 대조
    숫자 핵심 필드는 2중 추출 후 일치 여부 확인
    불일치/인용 실패 → "확인 필요" 플래그

[6] 초안 산출물 생성
    기존 형식과 동일한 data_XXX.sql 초안
    + 리뷰용 요약(필드별 근거 인용, 플래그 목록)

[7] 사람 검토 게이트 (변경 없음)
    GitHub PR로 올라옴 → 사람이 리뷰 → 머지
    실제 DB 반영은 지금처럼 사람이 run_sql.py 직접 실행
```

## 5. 실행 환경

**GitHub Actions 나이트 크론**을 제안한다.

- 현재 데이터 작업이 이미 "PR 생성 → 리뷰 → 머지" 흐름으로 운영되고 있다. 하네스의 산출물도 동일한 흐름에 얹으면, 새로운 신뢰 경계나 별도 검토 절차를 만들 필요가 없다.
- 매일 밤 정해진 시각에 대학 1~2곳 분량을 처리하고, 결과를 새 브랜치에 커밋해 **초안 PR을 자동으로 연다.** 사람은 다음 날 그 PR을 리뷰하면 된다.
- 팀원 개인 컴퓨터가 밤새 켜져 있어야 한다는 제약이 없어진다.
- 필요 준비물: Anthropic API 키를 GitHub Actions Secret으로 등록 (기존 Resend API 키를 Railway Variables에 등록했던 것과 같은 종류의 1회성 설정).

## 6. 명시적으로 채택하지 않은 방안과 이유

| 방안 | 왜 채택하지 않았나 |
|---|---|
| 에이전트에게 Supabase 쓰기 권한을 직접 부여, 사후에 문제 보고 | 검토 전에 이미 라이브 매칭 결과에 반영되어 버림. 문제가 있어도 실제 학생에게 노출된 뒤에야 발견됨. 자기 작업을 자기가 감사하는 구조라 같은 판단 오류를 반복해서 놓칠 위험도 있음. |
| "오래된 장학금"을 자동으로 삭제 | `application_deadline` 필드와 매칭 로직이 이미 마감 지난 장학금을 매칭 결과에서 자동으로 제외하고 있음. 행 자체를 지우는 건 필드만 정확히 채우면 불필요한 위험(복구 어려움, 실수로 유효한 항목 삭제)만 추가함. 프로그램 자체가 폐지된 경우만 별도 검토 대상으로 남김. |
| 에이전트의 "다 확인했다" 판단에 의존한 순회 | 장시간 작업에서 조기 종료·페이지네이션 누락이 실제로 관찰됨. 목록 수집을 결정적 코드로 옮겨 검증 가능하게 바꿈. |
| LLM으로 중복 판정 | 이름+기관 문자열 유사도만으로 충분히 신뢰할 수 있는 문제이고, 그쪽이 더 예측 가능함. LLM은 여기 쓰지 않음. |

## 7. 열린 질문 (검토 요청 사항)

1. **인용 대조의 임계값** — 원문과 완전히 동일한 문자열만 인정할지, 약간의 편집 거리(공백·문장부호 차이)를 허용할지. 너무 엄격하면 정상적인 추출도 과도하게 "확인 필요"로 빠질 수 있음.
2. **2중 추출 비용 대비 효과** — 숫자 핵심 필드에만 적용할지, 전체 필드에 적용할지. 비용은 크지 않지만(공고문 1건당 텍스트가 짧음) 리뷰 큐 크기와 트레이드오프가 있음.
3. **페이싱** — 밤마다 대학 1~2곳이 적절한 속도인지, 리뷰 부담을 고려했을 때 더 느리게/빠르게 가야 하는지.
4. **모델 선택** — 추출 정확도와 비용의 균형점. 추후 실제 공고문 샘플로 벤치마크 필요.
5. **최초 목록 수집(3.1절)의 실패 처리** — 게시판 구조 자체가 특이해 총 개수 파싱이 안 되는 학교가 있을 수 있음(이번에도 특정 단과대에서 실제로 발생). 이런 예외 케이스는 사람이 수동으로 처리하는 폴백이 필요.

**구현 시 결정된 값 — `harness/config.py` 참고** (1·2·3번은 상수/환경변수로 조정 가능, 4번은
아직 실제 벤치마크 전이라 기본값만 정함, 5번은 `CollectionResult.ok=False` + 로그로 사람에게
넘기는 것으로 구현):

- 인용 임계값: 정규화(공백/문장부호 차이) 후 완전 포함이면 확정, 그래도 없으면 `rapidfuzz`
  `partial_ratio` ≥ 92(기본값)일 때만 폴백 허용.
- 2중 추출 대상: `amount`, `min_age`, `max_age`, `max_income_bracket`, `min_gpa`,
  `language_test_min_score`, `min_grade`, `max_grade`, `application_deadline`.
- 페이싱: 나이트런당 대학 2곳(기본값), `HARNESS_UNIVERSITIES_PER_RUN` 환경변수로 조정.
- 모델: `claude-sonnet-5`(기본값), `HARNESS_EXTRACTION_MODEL` 환경변수로 조정.

## 8. 요약

이 설계는 기존에 제안된 "에이전트가 대학·학과 사이트를 전부 순회하며 자동 수집"이라는 아이디어를 그대로 살리되, 두 지점만 바꾼다: **(1) "다 봤는지" 판단을 에이전트가 아니라 코드가 하게 하고, (2) 추출한 값마다 원문 인용 근거를 강제해 기계적으로 검증한다.** 그리고 최종 반영은 지금처럼 사람이 검토한 뒤에만 이뤄지도록, 기존 PR 리뷰 흐름 위에 그대로 얹는다.
