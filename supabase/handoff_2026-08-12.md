# 데이터 작업 인수인계 (2026-08-12)

오늘 하루 동안 실사용자 UX 리서치에서 나온 버그 두 개(마감 지난 장학금 노출, 무관한 전공에
특기자 장학금 노출)를 고치면서 시작해서, 데이터 구조 자체를 점검하고 경쟁 서비스(이루리)
비교까지 진행함. 이 문서는 그 과정에서 발견했지만 이번엔 손 안 댄 것들, 그리고 앞으로도
계속 반복해야 하는 루틴을 정리한 것 — 다음에 이어받는 사람(또는 AI)이 이 문서만 보고
바로 시작할 수 있게 하는 게 목적.

오늘 실제로 뭘 고쳤는지는 git log(`git log --oneline` 2026-08-12 커밋들) 참고. 아래는
**앞으로 할 일**만 정리함.

### eligible_university NULL 294건(661건 중 44.5%) 전수 검증 — 우선순위 제일 높음
오늘 "확인 불가 조건이 문제가 아니라 구조가 문제" 논의 중 발견만 하고 손 안 댐. 체육특기자
사고랑 같은 클래스의 버그(조건은 있는데 구조화 필드가 비어서 전교생에게 노출)가 여기

있음. `description_gap_check.py`의 major 룰처럼, description에 특정 대학명이 언급되는데
`eligible_university`가 NULL인 케이스부터 스캔해볼 것.

## 2. 조사는 했지만 이번엔 보류한 것 (근거는 이미 확보됨)

### "확인 불가" 조건을 화면에 "직접확인 필요" 배지로 노출
`UNVERIFIABLE_CONDITIONS` 7종(부모직업/종교기관/출신학교/수능성적/내신/이수학점 잔여분/
비교과프로그램)은 필터링이 안 되고 랭킹만 밀리는데, 지금 유저 화면엔 이 사실 자체가 안
보임. 오늘 admission_track처럼 구조화 필드를 새로 만드는 대신, 이건 "필터링은 포기하되
투명하게 보여주기"가 맞는 방향이라고 결론 냈었음(구조적으로 못 푸는 문제라서). 프론트
`ScholarshipResults.tsx`/상세페이지에 배지 하나 추가하는 정도의 작업 — `backend/app/core/
matching.py`의 `unverifiable_condition_count()`가 이미 개수를 계산하고 있으니 그 값을
API 응답에 노출하기만 하면 됨.

### 부모직업 대분류 (소방/경찰/군인/농업인/소상공인/환경미화원 등)
이루리 회원가입 폼 비교하면서 발견 — `parent_occupation_condition`(확인 불가) 34건 중
남은 24건(교직원/동문 10건은 오늘 이미 분리함) 중 8~9건이 이 대분류로 승격 가능함을
확인함(id=74,238,298,640,927,982,1031,1132 등). 효과가 제일 작아서 오늘은 안 함 —
`data_collection_guide.md`의 특수상황 태그 목록에 추가하고 SpecialStatus enum에
`parent_occupation_firefighter_police`, `parent_occupation_military`,
`parent_occupation_farmer_fisher`, `parent_occupation_small_business` 정도로 나누면 됨
(오늘 rural_student/parent_university_* 추가한 패턴 그대로 재사용 가능).

### 가구원수(household size)
소득분위 계산에 이미 반영되긴 하는데, "가구원수 N인 이하만" 식으로 소득분위와 별개로
직접 조건 거는 장학금이 있는지 아직 DB에서 검증 안 함. 검증부터 먼저 할 것(있으면 필드
추가, 없으면 보류).

### 복수(이중/부)전공
지금 `department`는 학과 하나만 받아서 이중전공 학생이 두 번째 전공 관련 장학금을 놓칠
수 있음. 실제 DB에 이중전공 조건 건 장학금이 몇 건이나 있는지부터 확인 필요.

### 병역사항 "비대상" 명시적 추가
지금 `military_status`는 군필/면제/미필 3개뿐이라 여성 등 "해당없음"인 사람도 어쩔 수
없이 셋 중 하나를 골라야 함. "군필자만" 조건 건 장학금이 실제로 있는지 확인 후 판단.

## 3. 계속 정기적으로 돌려야 하는 것 (일회성 아님)

- **`supabase/tools/audit_description_gaps.py`**: 설명 텍스트엔 조건이 있는데 구조화 필드가
  비어있는 경우 탐지. 새 대학/장학금이 들어올 때마다, 또는 새로운 유형의 조건을 발견할
  때마다 `description_gap_check.py`의 `FIELD_GAP_RULES`에 키워드 추가하고 재실행.
- **`supabase/tools/audit_deadline_and_url_gaps.py`**: `application_deadline`/
  `application_url` 누락 스캔. Group B(200건, 반복공고 패턴이라 자동 처리 보류)는 여전히
  남아있음 — 사람이 원문 재확인해야 함.
- **`supabase/tools/audit_stale_application_period.py`**: 오늘 새로 만든 것. `application_
  period`에 "OOOO년 기준"처럼 이미 지난 연도가 박혀있는 경우 탐지. 이런 텍스트가 있는
  장학금은 매년 한 번씩 이 감사를 돌려서 재확인해야 함(특히 8~10월경 — 지자체/재단 장학금이
  몰려있는 시즌).
