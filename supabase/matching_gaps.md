### 3번 후속: `required_enrollment_status` 설계의 잔여 한계 (2026-07-30)

1. **"학부생·대학원생 둘 다 대상"을 표현 못 함** — 실제로 7건 있었음(KAIST 인성장학금 등). 지금은 비워둠(제한 없음)으로 처리해 결과적으로는 맞지만, 더 세밀한 조건(예: 휴학생만 제외)은 표현 안 됨.
2. **대학원생의 "휴학" 상태를 표현 못 함** — `undergrad_leave`만 있고 대학원 버전이 없음. "학생 출산·육아지원금"(KAIST)은 학부생 기준으로 근사 처리해서 대학원생 휴학 케이스는 놓칠 수 있음.

좁아짐 — id=1046과 동일한 이유). 근본 해결은 아래 원래 항목 참고.

### id=1046 인천 희망드림장학금 — 소득분위·특수상황·장애가 서로 다른 3개 메커니즘에 걸쳐 OR (2026-08-10 발견, 완전히 새로운 유형)

원문: "학자금지원구간6구간 이하 또는 기초생활수급자·차상위·한부모·중증장애인 등록자(OR조건)".
"6구간 이하"는 `max_income_bracket`, "기초생활수급자·차상위·한부모"는 `required_special_status`
(OR 리스트), "중증장애인"은 `requires_disability`(별도 필드) — 이 셋이 서로 다른 매칭 함수인데
전부 하나의 OR로 묶여야 함. 근데 `max_income_bracket` 체크는 `is_eligible()` 맨 앞쪽에서
다른 조건과 무관하게 무조건 먼저 거르는 독립 AND 게이트라(`backend/app/core/matching.py`),
지금 이 레코드는 이미 `max_income_bracket=6`이 걸려있는 채로 `required_special_status`는
비어있는 상태 — 즉 지금도 "6구간 이하"만 실질적으로 걸러지고 있고, 차상위·한부모·중증장애인
등록자인데 소득분위가 6구간보다 높은 학생은 원래 조건상 자격이 있는데도 지금 안 보이고 있을
수 있음(과소매칭 가능성).

**왜 이번에 못 고쳤는지**: 이번에 새로 만든 `required_special_status_all`(AND) 구조로는 이 3-way
OR을 표현 못 함 — 섣불리 `required_special_status`/`requires_disability`만 채우면
`max_income_bracket` 게이트가 여전히 먼저 걸려서 "6구간 이하 AND (장애 또는 태그)"로 오히려
더 좁아짐(기존보다 나빠짐). 그래서 이번엔 **데이터를 안 건드리고 여기 새 유형으로만 기록**함
(`추측으로 채우지 않는다` 원칙). 제대로 고치려면 `max_income_bracket`도 다른 조건들과 OR로
묶이는 경우를 표현할 방법(예: "이 필드는 다른 특정 조건과 OR"라는 플래그, 또는 자격조건을
그룹 단위로 표현하는 더 큰 구조 변경)이 필요 — 스키마 설계가 더 필요한 사안이라 별도 논의.

### 14번 후속: 거주지가 아니라 "출신 학교 소재지" 기준인 경우 (2026-08-03 발견)

한남대 "농어촌학생장학금"은 학생의 현재 거주지가 아니라 출신 고등학교 소재지가 농어촌 지역인지를 기준으로 함 — `eligible_region`/`UserSpec.region`은 애초에 "현재 거주지" 개념이라 담을 필드가 없음. `hometown_school_region_condition` 랭킹 태그로 일부 케이스 흡수 중이나(향우회/특정 학교 졸업생 조건 등도 이 태그로 흡수, 2026-08-06), 필터링 자체는 미해결.

### eligible_region의 시간(거주기간/전입시점) 정밀도 한계 (2026-08-06 발견)

`eligible_region`은 "지금 그 지역에 사는지"만 보는데, 실제로는 반대 방향 조건들도 있음: (1) "최근 3개월~1년 이내 전입한 사람만"(춘천 주소이전장학금 등 — 오래 산 사람이 아니라 최근에 이사 온 사람), (2) "30년 이상 계속 거주"(용인 향토장학금 — 훨씬 긴 기준). **사용자 결정(2026-08-07)**: 스키마 변경 없이 지역만 맞으면 노출하고, 기간 조건은 학생이 description 보고 스스로 판단하게 함. 발생 빈도 낮음(3~4건), 기록만 해둠.

### `required_degree_level` 단일값 한계 (2026-08-07 재검증에서 다수 발견)

"석사 또는 박사 둘 다 대상"인데 필드가 하나만 저장 가능해서 한쪽이 배제되는 경우가 12건
이상 발견됨(아산재단·숲과나눔 등). 1단계 반영 때 일부는 `required_degree_level=NULL` +
`required_enrollment_status="post_undergrad"` 조합으로 완화 처리했지만, 근본적으로
"석사 OR 박사만, 학부 제외" 같은 정밀한 조건은 여전히 표현 안 됨. 급하지 않음, 나중에
스키마 확장(예: 리스트로 변경) 논의 필요.

### `UNIVERSITY_GPA_SCALE`에 서울대학교 누락 (코드 이슈, 2026-08-07 id=1105 발견)

`backend/app/core/matching.py`의 `UNIVERSITY_GPA_SCALE` 딕셔너리에 서울대학교가 없어서, 4.3만점 기준인 서울대 학생 GPA가 4.5만점으로 자동 환산이 안 되고 원점수 그대로 비교됨 — 경계선 근처 학생이 부당하게 걸러질 수 있음. 데이터가 아니라 코드 수정 사항. 급하지 않음.

### 19번: 학생 본인 vs 부모 거주지역 OR 조건 (2026-08-05 발견, 설계 완료·구현 대기)

외부(재단/기업) 장학금을 새로 찾으러 다니다가 발견. 이미 운영 DB에도 몇 건 있었음 — 예:
- **2026년 재능키움 장학사업**(충남평생교육진흥원): "본인 또는 부모 중 1인이 충남에 1년 이상 거주"
- **화성시인재육성재단 주거비지원**: "본인 또는 부모 1인이 화성시에 1년 이상 거주"
- **인천 청년 해외배낭연수 장학생**(인천인재평생교육진흥원, 한밭대 크롤링 때 발견): "본인 또는
  부모의 주소지가 1년 이상 인천"

**영향**: `SavedSpec.region`(학생 본인 거주지) 하나만 있고 부모 거주지역을 입력받는 필드가 없어서,
**학생 본인 거주지는 자격 지역과 다르지만 부모님이 그 지역에 사는 학생**이 이런 장학금에서 부당하게
제외됨(실제로는 자격이 되는데 매칭 안 됨 — false negative). 반대로 `eligible_region` 자체의 값은
바뀔 필요 없음 — "충남"이라는 지역 값 하나면 충분하고, 문제는 그 값과 비교할 때 학생 쪽 정보가
한 개뿐이라는 것.

**벤치마크 조사(Scholarships.com)**: 참고할 선례가 있는지 확인차 스콜러십닷컴의 매칭 항목 23종
전체(`scholarships_com_전체항목_한국어정리.pdf`, 기존 9·10·12번 작업 때 쓴 것과 같은 자료)를
다시 훑어봄. 결과: **거기도 "부모 거주지역"이라는 별도 필드는 없음.** 지역 관련 항목은 "거주 주
(Residence State, 본인이 사는 곳)"와 "재학 예정 주(School Attendance State, 학교가 있는 곳)"
두 축으로만 나뉘어 있고, "본인 또는 부모"를 명시적으로 묶어서 다루는 항목은 **"소속 직장
(Employer)"** 하나뿐(본인/부모 직장을 분리 안 하고 하나의 필드로 합쳐서 처리). 즉 우리가 지금
겪는 "거주지역에서의 본인/부모 OR 조건"과 똑같은 선례는 없었음 — 참고만 하고 사용자가 직접 결정.

**사용자 결정(2026-08-05)**: 부모 거주지역을 **직장(Employer)처럼 하나로 합치지 않고, 본인
거주지역과 별개의 필드로 따로 만들기로 확정.** (참고: 16번 "부모 직업/소속" 조건은 이번엔 같이
안 하기로 하고 보류 — 그쪽은 카테고리가 고정된 목록이 아니라 계속 늘어나는 유형이라 설계가
더 오래 걸림, 나중에 별도로.)

**설계(구현 시 필요한 변경)**:
- `Scholarship` 테이블: **변경 없음.** `eligible_region`은 지금처럼 "인정되는 지역 값 하나"만
  담으면 됨 — 이 필드가 "본인 기준"인지 "부모 기준"인지 구분할 필요가 없음(둘 중 하나만 맞아도
  통과이므로 대상 지역 값 자체는 동일).
- `SavedSpec`(및 `UserSpec`)에 `parent_region: str | None` 추가 — 본인 `region`과 동일한 옵션
  목록(`frontend/src/lib/regions.ts`의 `SIDO_LIST`) 재사용, **선택 입력**(모르면 비워도 됨,
  비우면 "부모 조건 불일치"로만 처리되고 본인 조건은 별개로 그대로 평가됨).
- `backend/app/core/matching.py`의 `is_eligible()` (현재 line 203):
  ```python
  if scholarship.eligible_region is not None and spec.region not in scholarship.eligible_region:
      return False
  ```
  →
  ```python
  if scholarship.eligible_region is not None:
      own_match = spec.region in scholarship.eligible_region
      parent_match = spec.parent_region is not None and spec.parent_region in scholarship.eligible_region
      if not (own_match or parent_match):
          return False
  ```
- 프론트(`frontend/src/app/spec/page.tsx`, `frontend/src/lib/spec.ts`, `frontend/src/app/mypage/page.tsx`):
  "광역자치단체/기초자치단체" 입력 칸 바로 아래에 "부모님 거주지역"용 칸을 동일한 UI로 하나 더
  추가(선택 입력이라고 명시).
- **데이터 재작업은 불필요** — 기존 366건의 `eligible_region` 값은 그대로 두면 됨(위 설계 이유
  참고). 다만 "본인 또는 부모" 문구가 description에 있는데 `eligible_region`이 아예 안 채워진
  건이 있는지 확인하는 감사(audit)는 필요 — 아래 `EXTERNAL_SCHOLARSHIPS_PLAN.md` 참고.

상세 결정 기록은 `SCHEMA_DECISIONS.md`에도 남김.

## 그 외 호성과 논의할 사항 (자격조건 매칭과는 별개)

1. **UserSpec 저장** — 🔶 부분 해결(2026-07-29): 로그인 없이 프론트 `localStorage`에 클라이언트 저장하는 방식으로 일단 재입력 부담은 줄임. 서버 쪽 진짜 계정/프로필 저장은 아직 없음 — 나중에 로그인 도입 여부 결정 필요.
2. **DB에 중복 방지 제약이 없음** — 지금 중복 제거는 `scholarship_dedup_list.md`를 사람이 손으로 대조하는 방식뿐. 대학이 늘어날수록 깨지기 쉬움 — `name+provider` 유니크 제약이나 INSERT 전 자동 중복검사를 백엔드에 둘지 논의.
3. **마감일 자동 정리** — 대학이 늘어나면 이미 넣은 장학금들의 마감이 하나둘 지나갈 텐데, 주기적 재크롤링/정리 계획이 필요한지, 구조화된 deadline 컬럼으로 자동 필터링할지 방향 결정 필요.
4. **`data_baejae.sql`·`data_hanbat.sql`의 배치1 행 컬럼 개수 불일치** (2026-08-02 발견) — 두 파일 다 실제 값 개수가 헤더보다 1개씩 부족. 라이브 DB에는 이미 정상적으로 들어가 있어서 서비스에는 영향 없음 — 이 두 백업 파일을 재적재(reseed)할 일이 생기기 전까지는 급하지 않아서 보류.
