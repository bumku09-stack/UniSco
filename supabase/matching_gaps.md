## 확인된 사실 (backend/app/models/ 코드 기준, 2026-07-30)

`UserSpec`(사용자 입력값): `university`, `college`, `gpa`, `age`, `gender`, `region`, `military_status`, `income_bracket`, `has_disability`, `is_foreigner`, `enrollment_status`, `grade`, `degree_level`.

`scholarship` 테이블에서 실제로 매칭되는 필드(`backend/app/api/match.py`): `min_age`/`max_age`, `required_gender`, `eligible_region`, `required_military_status`, `max_income_bracket`, `min_gpa`, `requires_disability`, `foreigner_eligibility`, `eligible_university`, `eligible_college`, `required_enrollment_status`, `min_grade`/`max_grade`, `required_degree_level`.

기존 133건 중 128건은 이 신규 필드까지 실제 값으로 백필 완료(2026-07-30, `SCHEMA_DECISIONS.md` 참고). 나머지 필드(`grade_level`, `major`, `affiliated_institution`, `min_credits`, `admission_score_condition`, `headcount`, `application_period`, `category_l1`/`category_l2`)는 **컬럼은 있지만 매칭 로직에서는 전혀 안 쓰임**(`category_l1`/`l2`는 애초에 자격조건이 아니라 분류용이라 매칭 대상이 아닌 게 의도된 설계).

## GPA 관련 참고 (혼동 방지용)

`min_gpa`(장학금 쪽 최소학점 조건)는 **이미 컬럼도 있고 데이터도 채워지고 있음** — 크롤링 중 등급→GPA 환산 기준을 대학마다 한 번 확정해서 적용 중(예: 충남대 A0=4.0/4.5만점, KAIST는 4.3만점제 별도 환산표 사용). 이건 갭이 아님.

### 9번 후속: OR로 묶인 복합조건 장학금 재분류 (2026-08-03, 사용자 지시)

처음엔 "여러 조건이 OR로 묶인 장학금은 단일 값으로 못 정한다"는 이유로 4건을 재분류 대상에서 뺐었는데, 사용자가 "OR면 그냥 여러 개 넣어서 하나만 맞아도 뜨게 설계하면 되잖아"라고 지적해서 `required_special_status`를 리스트로 바꾸고 재분류함. 각 건별 처리:

- **배재사랑장학금**(배재대, "장애학생 또는 다문화가정 학생"): `requires_disability=TRUE`(기존에 비어있던 걸 채움) + `required_special_status=['multicultural_family']`. 장애 조건과 특수상황 조건이 둘 다 걸려있어서 `is_eligible()`이 이 둘을 OR로 처리함(위 표 9번 설명 참고).
- **희망복지장학금**(배재대, "기초생활수급자·차상위계층·한부모가족"): `required_special_status=['basic_livelihood_recipient', 'near_poor', 'single_parent_family']`. 순수하게 특수상황 리스트 안에서의 OR라 장애 조건과의 OR-그룹 로직은 안 걸림(표준 `special_status_matches()` 그대로 적용).
- **장학사정관장학금**(대전대): 7개 세부조건 중 5개(다자녀/중증질병 및 상해/실직가정·재난 및 재해/긴급가계곤란/다문화가정자녀)만 `required_special_status`로 구조화함(`multi_child_family`/`severe_illness_or_injury`/`job_loss_or_disaster`/`financial_emergency`/`multicultural_family`). **나머지 2개는 구조화 안 함**: "희망장학금(부모 중 장애등급 1~3급)"은 학생 본인이 아니라 **부모**의 장애라 `requires_disability`(본인 장애 여부)로 표현하면 틀림 — `DisabilityType.DISABLED_PARENT` 값 자체는 있지만 `disability_matches()` 로직이 `spec.has_disability`(본인 장애)를 전제로 하고 있어서 이 케이스엔 못 씀(기존에도 있던 설계 상 허점, 이번에 새로 발견). "기타 경제적 어려움 소명자"는 명시적 catch-all이라 애초에 구조화 불가능. 둘 다 `description` 텍스트로만 유지.
- **봉사공로 장학금**(대전대): 9개 세부항목 중 "학생회임원봉사" 하나만 `required_special_status=['student_council_officer']`로 구조화함. 나머지 8개(국외봉사 참가자, 외국인봉사, 각종 행사 참여자, 행사공로, HRC, 푸른별홍보대사, 입시홍보, 학군단)는 "신분·상황"이 아니라 "특정 활동 참여·수상 이력"이라 성격이 달라서 `special_status` 타입에 안 맞음 — 이런 활동 이력을 담을 필드 자체가 없어서 구조화 못 함, `description` 텍스트로만 유지.
- **을지대 "면학장학금"(id 304)은 그대로 둠**: "다자녀가구"가 독립된 OR 조건이 아니라 특정 소득분위 구간(1~2 또는 8구간) 안의 하위 조건이라, `required_special_status`에 다자녀를 넣으면 오히려 다른 소득분위 조건으로 자격되는 학생을 잘못 걸러내게 됨 — 그대로 `description` 텍스트만 유지.

**새로 발견된 갭(부모 장애 케이스)**: `DisabilityType.DISABLED_PARENT`가 프론트 장애인유형 드롭다운에 있는데, 이 드롭다운 자체가 "장애인" 토글(본인 장애 여부, `has_disability`)을 켜야만 열리는 구조라(`frontend/src/app/spec/page.tsx`), 본인은 장애가 없고 부모만 장애가 있는 학생은 애초에 이 값을 선택할 방법이 없음(장애인 토글을 켜면 본인이 장애인이라고 잘못 주장하는 셈이 됨). 이건 스키마 문제가 아니라 UI 설계 문제라 이 문서에 기록만 해두고 직접 고치진 않음(프론트에 "본인 장애"와 "부모 장애"를 별도 질문으로 분리하는 리디자인이 필요해 보임 — 호성·사용자 논의 필요).

### 특수상황 매칭 로직 (2026-08-02, 사용자 확정 — 다른 필드들과 다른 예외 규칙)

다른 필드(성별·나이·GPA 등)는 전부 "장학금에 조건이 있으면, 유저가 그 조건에 안 맞을 때 제외" 방식임. **특수상황은 이거랑 다르게, "유저가 특수상황을 아예 선택 안 했으면 애초에 걸러내지 않는다"는 예외 규칙**을 사용자가 명시적으로 요구함:

- **유저가 특수상황을 하나도 선택 안 함** → 특수상황 조건이 걸려있는 장학금도 걸러내지 않고 그냥 다 보여줌 (마치 특수상황 필드 자체가 없는 것처럼 동작).
- **유저가 특수상황을 1개 이상 선택함** → 그때부터 특수상황 조건이 걸려있는 장학금만 필터링 시작: 유저가 선택한 항목과 장학금이 요구하는 항목이 일치하면 보여주고, 안 맞으면 제외. **특수상황 조건이 아예 없는 일반 장학금은 이 필터링과 무관하게 계속 다 보임.**

**이유(사용자 설명)**: 특수상황은 선택 항목(옵션)이라 안 누른 학생이 많을 텐데, "안 눌렀다"는 게 "나는 특수상황 대상자가 아니다"를 확정하는 게 아님 — 그냥 아직 대답 안 한 것뿐. 그런데 표준 방식대로 처리하면, 실제로는 다문화가정인 학생이 그 항목을 안 눌렀다는 이유만으로 다문화가정 전용 장학금이 안 보이게 될 수 있음 — 그건 잘못된 결과. 그래서 "선택 안 함 = 모르는 것 = 걸러내지 않음", "선택함 = 그 항목 기준으로만 좁힘"으로 설계함.

실제 구현(2026-08-03, `backend/app/core/matching.py`) — `required_special_status`가 리스트라 "장학금 쪽 여러 특수상황 중 하나 + 유저 쪽 여러 특수상황 중 하나"가 겹치는지 보는 형태로 확장됨:
```python
def special_status_matches(scholarship_special_status: list[SpecialStatus], spec_special_status: list[SpecialStatus]) -> bool:
    if not scholarship_special_status:
        return True  # 특수상황 조건 없는 일반 장학금 — 항상 통과
    if not spec_special_status:
        return True  # 유저가 특수상황 아예 안 눌렀음 — 그래도 걸러내지 않음
    return bool(set(scholarship_special_status) & set(spec_special_status))  # 하나라도 겹치면 통과
```
`is_eligible()`에는 이 표준 버전 대신, 장애 조건과 OR로 묶일 때만 "안 누르면 통과" 예외가 없는 `special_status_matches_strict()`를 씀(위 9번 후속 참고) — 안 그러면 `has_disability=False`처럼 이미 확실한 "아니오" 답이 있어도 특수상황 쪽 예외 때문에 OR 전체가 사실상 항상 True가 돼버림.

### 2번 후속: 학과(department) 데이터 — 2026-08-03 세 단계로 완료

`frontend/src/lib/universities.ts`의 `CollegeInfo` 타입(`{ name: string; departments: string[] }`)으로 대학→단과대→학과 3단 구조를 만들었고, `/spec`·`/mypage` 둘 다 단과대 선택 후 학과를 고르는 드롭다운이 뜨도록 연결 완료. 백엔드 매칭(`major_matches()`)도 동작함.

**1단계(처음 구현 시)**: 을지대 의과대학 말고는 실제 학과 이름을 안 채우고 구조만 먼저 만들어뒀었음 — 사용자가 "드롭다운으로 안 뜬다"고 지적해서, 우선 학과 목록이 없는 단과대는 화면에서 자유 텍스트 입력으로 자동 대체되도록 폴백을 추가함(빈 드롭다운 대신 "예: 컴퓨터공학과" 같은 직접 입력 칸). 그런데 사용자가 "그것도 드롭다운으로 만들라"고 재지시해서 2단계 진행.

**2단계(실제 조사, 2026-08-03)**: 9개 대학(을지대 제외) 각각에 대해 병렬 조사 에이전트를 띄워 단과대별 실제 학과 목록을 공식 사이트에서 찾아 `universities.ts`에 채워 넣음.

- 한밭대 "정보통신대학"이 실제로는 "정보기술대학"으로 개편됨(정보통신공학과는 AI융합대학으로 이동) — 자동 조사 단계에서 발견.

### 3번 후속: 백필하면서 새로 발견된 한계 (2026-07-30)

기존 133건 중 128건에 실제 값을 채우면서 확인된, `required_enrollment_status`(`undergrad_enrolled`/`undergrad_leave`/`post_undergrad` 3택1) 설계의 한계:

1. **"학부생·대학원생 둘 다 대상"을 표현 못 함** — 실제로 이런 장학금이 7건 있었음(KAIST 인성장학금, 한국원자력학회장학금, 두산중공업장학금, 학생자치단체 간부장학금 3종, 감민호장학금). 지금은 그냥 비워둠(제한 없음)으로 처리했는데, 이게 결과적으로는 맞지만(둘 다 통과되니) — "휴학생은 제외하고 재학 중인 학부/대학원생만"처럼 더 세밀한 조건은 표현이 안 됨.
2. **대학원생의 "휴학" 상태를 표현 못 함** — `undergrad_leave`만 있고 대학원 버전이 없음. "학생 출산·육아지원금"(KAIST, 휴학 중인 사람 대상)은 학부생 기준(`undergrad_leave`)으로 근사 처리함 — 대학원생이 이 사유로 휴학 중이면 지금 시스템에서 놓치게 됨.
3. **법학전문대학원(로스쿨) 계열이 분류 체계에 안 맞음** — ✅ **부분 해결 (2026-07-31)**. `frontend/src/lib/universities.ts`의 충남대 단과대 목록에 `법학전문대학원`/`의학전문대학원`을 추가하고, 로스쿨 장학금 4건(id 15·16·43·44)은 `eligible_university=충남대학교`/`eligible_college=법학전문대학원`/`required_enrollment_status=post_undergrad`로, MD-Ph.D 통합과정 1건(id 92)은 같은 방식+`eligible_college=의학전문대학원`으로 분류함. `required_degree_level`은 JD형 전문대학원엔 맞는 값이 없어서 비워둠(제한 없음) — 어차피 `eligible_college`로 이미 좁혀지니 결과적으로는 문제없음. 다만 MD-Ph.D의 `required_degree_level=integrated_ms_phd`는 정확한 값이 없어서 가장 가까운 값으로 근사 처리한 것 — 정식으로 JD/MD-PhD 전용 값을 enum에 추가할지는 호성과 논의 필요.

### 13번: GPA "직전학기" vs "전체(누적)" 구분 — ✅ 2026-08-02 구현, ✅ 2026-08-03 "둘 다" 변형까지 완료

우송대 장학금 재검증 중 사용자가 발견: 같은 대학 안에서도 어떤 장학금은 **직전학기 성적만** 보고(예: 우송대 성적우수 교내장학금 "자립/단정/독행/협동" — 직전학기 평점평균 3.0이상), 어떤 장학금은 **전체 재학기간 누적(CGPA)** 을 보거나(예: 우송대 국제학생 대상 "글로벌 유학생 성적A~E" — "GPA(직전학기) 또는 CGPA(전체학기) 평균"), 아예 두 기준 중 유리한 쪽을 인정해주는 경우도 있음.

**해결 내역**: `scholarship.min_gpa_basis`(`GpaBasis` enum) 컬럼으로 `semester`/`cumulative`/`both`/NULL(미지정, 둘 중 하나만 맞아도 통과하는 관대한 기본값) 4가지를 구분함. `UserSpec`/`SavedSpec`도 `semester_gpa`/`cumulative_gpa` 두 칸으로 나눠서 받음(2026-08-02). 2026-08-03에 을지대 "차세대의료인장학금"(전체누적+직전학기 **둘 다** 동시 충족 필요)이 발견되면서 `both` 값을 추가하고 `core/matching.py`의 `gpa_matches()`에 반영함 — 이제 4가지 케이스(직전학기만/전체누적만/둘 다/미지정) 전부 구조화된 컬럼으로 표현 가능.

### 14번: 지자체 장학금의 거주지 세부단위(시/군/구) 매칭 (2026-08-02 발견)

한밭대 크롤링 배치에서 미확인으로 남겨뒀던 지자체 장학금 5건을 재검증하면서 발견: "울산 남구 우듬지인재키움"(울산 남구 거주자만 대상)이나 "익산시 대학생 학자금 이자지원"(익산시 거주자만 대상)처럼, **시/도 전체가 아니라 그 안의 특정 시/군/구 단위로만 자격을 제한하는 지자체 장학금**이 있음. 그런데 `frontend/src/lib/spec.ts`의 `region` 값은 `regionShortName()`을 거치면서 구/군 정보가 사라지고 시/도 단위(예: "울산", "전북")로만 저장됨(`regionShortName` 주석 참고: "region은 구/군 정보 없이 짧은 시/도 단위로만 저장돼 있어서"). 그래서 이런 시/군/구 단위 장학금을 `eligible_region`에 그대로 넣으면(예: "울산") 실제로는 자격이 안 되는 다른 구(중구·동구·북구·울주군)의 울산 거주자한테도 잘못 매칭되는 과다매칭(false positive) 문제가 생김.

- **영향**: 이런 장학금은 `eligible_region`을 비워두면 아예 안 걸러지고(과다노출), 시/도 단위로만 채우면 부정확하게 걸러짐(과다매칭) — 둘 다 틀림.
- **제안(호성 검토 필요, 스키마/프론트 변경 사안)**: `SIDO_LIST`(`frontend/src/lib/regions.ts`)의 구/군 목록을 활용해서 `region` 저장 시 구/군 정보도 유지하도록 바꾸거나, `eligible_region`을 "시/도" 텍스트 하나가 아니라 구조화(시/도+구/군)해서 정확히 비교하는 방식 검토.
- 크롤링 데이터 입력 시 임시 방침: 시/도 전체가 대상인 지자체 장학금(예: 인천·전북 전역)은 `eligible_region`에 시/도 단위 텍스트를 그대로 넣어도 안전하지만, 시/군/구 단위로 좁혀진 장학금(우듬지인재키움·익산시 사례)은 **`eligible_region`을 비워두고 `description`에 정확한 대상 지역을 텍스트로만 명시**하는 걸로 유지(과다매칭보다 과다노출이 덜 해로움 — 사용자가 설명을 읽고 스스로 판단 가능).

— 나머지 8개 대학 백업 파일은 구버전 스키마라 이 컬럼 자체가 없어서 동기화 대상에서 제외(아래
"그 외 호성과 논의할 사항" 6번에 이미 기록된 기존 문제, 이번에 새로 발견한 건 아님).

**검증**: synthetic 테스트 9종(leniency 제외 확인, 노출 불변 확인, 어학점수 버그 수정 확인 등)
전부 통과 + 운영 DB 실측 매칭 시뮬레이션(CNU 공대 3학년 샘플)으로 "확인 불가 태그 있는 장학금은
예외 없이 태그 없는 장학금보다 순위가 낮다"는 것 전수 확인함.

**같은 날 후속 수정**: 실사용 중 "북한이탈주민 대상" 장학금이 여전히 상위 노출되는 걸 사용자가
발견 — 원인은 `confirmed_match_count()`에서 소득분위/특수상황/어학점수를 "학생이 안 답했으면
보너스만 안 줌"까지만 했고, `unverifiable_condition_count()`(감점 대상)엔 안 넣었던 것. 즉 다른
조건(대학·단과대 등)만 잘 맞으면 특수상황 감점 없이도 상단에 뜰 수 있었음. `unverifiable_condition_count()`
가 `spec`도 받게 바꿔서, 소득분위 모름/특수상황 안 고름/어학점수 안 넣음인데 그 조건이 걸린
장학금도 8개 "확인 불가" 태그와 동일하게 감점 대상에 포함시킴(노출 여부는 그대로, 순위만 밀림).
학생이 실제로 그 항목에 값을 넣었는데 안 맞으면 애초에 `is_eligible()`에서 걸러지니 여기까지
안 오고, 실제로 맞으면(예: 진짜 북한이탈주민이라고 고름) 감점 없이 오히려 보너스까지 받음 —
회귀 테스트로 확인함.
